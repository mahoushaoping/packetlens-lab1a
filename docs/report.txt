摘要
本实验实现一个具备真实网络捕获能力的图形化嗅探器。底层通过 ctypes 调用系统 libpcap，使用显式字
节解析完成链路层、网络层、传输层与常见应用层协议分析。界面包含包列表、协议字段树、HEX/ASCII
字节视图，提供 BPF 抓包过滤、逻辑显示过滤、PCAP 保存与读取，以及双向 TCP 流追踪。
macOS 26.2 / Apple Silicon 环境已完成 21 项核心自动化测试与实际 Tk
窗口集成测试；经用户在本机授权执行的 4 秒回环抓包验收，捕获 12 个包并识别两个 HTTP
头部，相关丢包计数为 0。性能结果仅代表该有界功能验收，不表示高吞吐能力。

02 / 环境与复现步骤
运行环境
主要验收平台为 macOS 26.2 arm64；Python 3.12 与 Tk 9.0.4。应用仅依赖 Python 标准库与系统
libpcap，不依赖 Scapy 或 Wireshark。推荐使用带 Tk 的 Python
3.10+。本机启动脚本依次查找指定解释器、python.org 安装路径、已有 Codex Python 运行时及 PATH
中的 python3。
离线启动：不需要管理员权限
cd "实验1A_src"
python3 main.py --demo
# 或双击源码目录中的 启动.command
如果当前 python3 没有 Tk，可从 python.org 的 macOS 下载页安装带 Tk 的 Python，再设置
PACKETLENS_PYTHON 指向其绝对路径。应用无需执行 pip install。requirements-dev.txt
只用于生成报告与视频素材。
最短操作路径
点击“演示样本”加载 17 个合成包；点击 HTTP / DNS / IPv6 按钮过滤；选择一行查看字段和原始字节；对
TCP、HTTP 或 TLS 包使用“追踪 TCP 流”；通过两个方向标签查看重组数据。“导出可见包”只导出当前显
示过滤命中的包。新会话覆盖当前数据前会提示保存。
真实抓包验收
python3 -m unittest discover -s tests -v
python3 tools/gui_smoke.py
# 下面命令需要管理员权限，仅抓本机实验端口 4 秒：
sudo /absolute/path/to/python3 tools/verify_live.py test-output
将 /absolute/path/to/python3 替换为实际解释器绝对路径。verify_live.py 创建 127.0.0.1:8765 的临时
HTTP 服务，禁用环境代理，经 libpcap 抓取对应流量，4 秒后等待线程退出并保存 PCAP 与 JSON
收据。它不修改 /dev/bpf 权限，不连接外部主机。
日常 GUI 实时捕获需要运行进程具有 BPF 访问权限。当前普通用户首次打开 lo0 会收到权限错误，这是
macOS 设备访问控制；离线模式仍可使用。选择 lo0、BPF 填 tcp port 8765，开始后另运行
tools/local_traffic.py 即可产生本机测试流量。
兼容范围
代码为 Linux libpcap、Windows Npcap
预留库加载和链路解析分支，但本次没有在这两种系统实际验收。Linux 需安装 Tk 与 libpcap；Windows
需 Python 的 Tcl/Tk 组件和 Npcap。提交以 macOS 成功运行证据为准。

libpcap 调用链
pcap_findalldevs -> pcap_open_live
  -> pcap_compile -> pcap_setfilter -> pcap_freecode
  -> pcap_setnonblock(1) -> pcap_next_ex (bounded loop)
  -> pcap_stats -> pcap_close
捕获句柄只由工作线程持有；主线程通过 stop_event
请求退出，不跨线程关闭句柄。每个有效数据包在下一次 libpcap 读取前复制成 Python
bytes，避免保留失效指针。非阻塞读取无数据时等待 10 ms，兼顾停止响应和 CPU 占用。[1]
资源界限与界面响应
默认捕获 60 秒或 10000 包，允许配置 1..3600 秒；GUI 保存上限为 10000 包或 32 MiB
原始字节。工作队列容量 2048，满时丢弃新事件并计数；主线程每约 80 ms 最多消费 200 包。PCAP
读取也分批执行，防止长文件阻塞 UI。32 MiB 是原始字节上限，不含 Python 对象、控件和队列内存。
结束或出错时，finally 释放过滤器或句柄。窗口关闭先请求停止，等 worker 退出再销毁 Tk。界面区分
libpcap 内核统计与程序队列丢包；不同平台的 received 统计口径可能不同，不能直接当作 BPF
后的包数。

04 / 协议解析与应用层识别
层次
主要解析与边界
链路层
Ethernet、最多 4 层 VLAN；macOS NULL/LOOP 回环；Linux SLL/SLL2；Raw IP
网络层
ARP 地址与操作；IPv4 IHL/总长度/分片/TTL；IPv6 地址、payload length、最多 16 个扩展头
传输层
TCP 端口、Seq/Ack、标志、窗口、数据偏移；UDP 长度；ICMP/ICMPv6 类型与代码
HTTP
根据请求方法及 HTTP/1.x 起始行或响应起始行识别，显示头部文本
DNS
53 端口上解析报头、问题、应答；名称压缩指针和循环检查；A/AAAA 与部分名称 RDATA
TLS
识别记录类型、记录版本、长度；不声称解密 HTTPS
解析顺序与安全边界
每次读取固定字段前执行 require(data,
size)；可变长头部检查最小值与已捕获字节数。报文解析失败时保留已识别的协议层和原始帧，增加
warnings，而不是让窗口崩溃。IPv4/IPv6 真正分片不继续伪装成完整 TCP 包；本实现未做 IP
分片重组。
HTTP 不是通过“端口 80”判定：测试中在端口 8765 发送 GET / HTTP/1.1 能被识别，而端口 80
上的任意字节仍保持 TCP。DNS 同时利用端口和结构检查；TLS
是记录头启发式识别，可能存在误判，并非完整握手状态机。
包与流的区别
一个 HTTP 头部可能被拆成多个 TCP
段，也可能多个应用消息合在一个段里。当前包列表按单包载荷识别；没有起始行的后续片段可能显示为
TCP。应使用流追踪重组字节后阅读跨段内容，而不能仅导出 HTTP 过滤结果就声称得到完整 HTTP
会话。
本次明确未覆盖
不校验实际捕获报文的 TCP/UDP 校验和（网卡卸载也会影响观察）；不支持 HTTP/2、HTTP/3、TLS
解密、完整 DNS 扩展记录、IPv6 jumbogram、Wi-Fi Radiotap 解码。未知链路或协议仍保留 HEX
视图。合成样本生成器会计算基本 IP/传输层校验和。

05 / 双层过滤器与 TCP 流算法
抓包过滤：BPF
BPF 交给 libpcap 编译并安装，在捕获开始时生效，例如 tcp port 8765、ip6 and udp port
53。它减少传入应用的数据量。HTTP 不是本程序添加到 libpcap 的关键字，应先用 TCP/端口等 BPF
粗筛，再使用显示过滤分析应用层。[1][2]
显示过滤：不执行任意代码
expr := term ("or" term)*
term := atom ("and" atom)*
atom := "not" atom | "(" expr ")" | predicate
tcp and (port 80 or port 8765)
http or dns
ipv6 and not udp
host 127.0.0.1 and contains get
支持协议名、host/src/dst IP、port、contains 单个 ASCII 词；优先级 not > and > or。最多 2048
字符、128 token，不调用 eval。contains 在单包 payload 上做不区分 ASCII
大小写的匹配，不支持带空格的引号短语。表达式错误时保留原过滤结果并显示错误。
双向 TCP 流追踪
流键是排序后的两个 (IP, port) 端点；分别处理两个发送方向。以 SYN
后一个序列号为锚点，缺少握手时使用首个观察到的载荷序号。将 32 位序号映射为相对有符号偏移，按
偏移及包号排序，顺序拼接尚未覆盖的字节；重复或重叠部分计入去重数；缺失区间用文字标记，不用零
填充伪造数据。[3]
relative = ((seq - anchor + 2**31) % 2**32) - 2**31
overlap = max(0, cursor - relative)
append(payload[overlap:])
合成样本把响应后半段提前送达，并重复发送前 35 字节。重组后响应恢复为 HTTP/1.1 200 OK 与 Hello,
PacketLens!，重复字节数为 35，缺失为 0。另有专门测试覆盖序号回绕、部分重叠与初始缺口。
限制：同一四元组的多次连接可能合并；相对偏移算法假设单方向观察跨度小于 2^31 字节；不是完整
TCP 状态机。冲突重叠按较早序列起点优先，同起点按首见包优先，不模拟各操作系统的重组策略。

08 / 原理讨论、局限与提交说明
OSI 模型与课件思考题
OSI 将网络功能划分为物理、数据链路、网络、传输、会话、表示、应用七层。本程序从链路层或回环伪
链路抓取数据，自行向上解析；实际 TCP/IP 模型不必逐一对应 OSI
的所有层。抓取位置决定能观察到哪些信息，协议分析器决定怎样解释这些字节。
Thor 一类工具可通过代理或系统网络扩展观察应用请求，并在信任根证书且应用允许的条件下参与 TLS
连接，因此能够展示部分 HTTPS 明文。这不意味着它获得了原始 TCP
的每个段、重传或内核状态。反过来，链路层嗅探器可见 TCP 字段，但没有相应会话密钥就不能从 TLS
密文直接恢复 HTTP。证书固定等机制也会限制代理解密。
加分项与可继续改进的方向
已实现双向 TCP 流追踪。未实现进程到所有 TCP 流的归属追踪；下一步可研究平台 socket
表与进程事件接口。工程上可加入按连接代次分离、完整重传冲突策略、IP 分片重组、增量 HTTP
解码、统计时序图以及更高吞吐的抓包/显示隔离。当前版本定位为可解释、可复现的课程实验。
